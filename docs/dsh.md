# DeepSeek Harness conversations

Settings → Agents and the setup guide list DeepSeek Harness as `dsh-tui`, the name herdr gives a dsh-tui pane. It counts as installed when both `dsh-tui` and `dsh` are found, since dsh-tui alone cannot start a session; the version shown is dsh-tui's. dsh-tui is the binary looked for first because Debian's distributed shell is a `/usr/bin/dsh` too (which would still pass as the `dsh` it needs). Install runs its makers' `npm install -g @deepseek-ai/dsh @deepseek-harness-tui/dsh-tui` in a terminal tab. dsh-tui's first start sets up its profile with pnpm (on a fresh dsh home, dsh 0.2.1-rc.5 refuses dsh-tui 0.17.0 as an untested pair until the `dsh plugin --profile dsh-tui allow-version … --accept-risk` command it prints in that tab is run; the catalog's `known_issues` record it), then asks for a model in its own prompt: a DeepSeek API key (from https://platform.deepseek.com/api_keys) or an OpenAI- or Anthropic-compatible provider. Sign in in the setup guide opens that prompt in a terminal tab; Ovis has no field of its own that asks for the key; on a phone, type it on the terminal's keyboard rather than the input line, which keeps an unsent line in the browser until it is sent (#2523). New workspace, New tab and New worktree start it by typing `dsh-tui`'s path into the pane's shell, as for omo and gjc: herdr's `agent start` has no dsh kind. Windows is not offered at all (no install, no start): Ovis cannot start it there yet. A Debian PC with the unrelated distributed shell at `/usr/bin/dsh` and only dsh-tui installed still reads as installed; its start then fails in the tab.

On Linux, the chat lens reads the native DeepSeek Harness v4 session log. It supports plain JSONL and concatenated Zstandard frames. dsh has no chat interface of its own in a terminal: one comes from a profile plugin such as dsh-tui (`dsh --profile dsh-tui`) or dsh-tui-pi (`dsh --profile tui`), or from one-shot `dsh --profile headless` runs. A pane is read as dsh when herdr labels it `dsh-tui` (dsh-tui reports itself to herdr) or, when herdr names no agent, when its foreground process is the dsh launcher booting a chat profile: `node …/bin/dsh` or `node …/@deepseek-ai/dsh/lib/bin.js`, then `--profile <name>` or the name, or dsh-tui's host process (`node …/@deepseek-harness-tui/dsh-tui/lib/…/host-entry.js`), which `dsh-tui` runs behind its two launcher shims and which holds the lock. Plugin management, config dumps and the `web`, `sdk`, `sdk-minimal` and `acp` profiles are not chats and keep the terminal. That check reuses the `pane.process_info` answer Ovis already asks for an unlabeled pane, so a dsh pane costs no extra RPC; a labeled one asks once per lookup, for omo and for the binding together.

The reader identifies the session through the `session.lock` file held open by the pane's foreground dsh process, in a session directory named by its UUID (the TUIs) or `session-<UUID>` (headless). It does not select a session by directory or modification time. A new idle dsh process with no session lock, started after the Ovis server, shows an empty chat until its first message creates the log. A TUI that idles long enough releases its lock (dsh disposes the session); its pane then uses the terminal fallback until the next message, and so does a lock-free dsh that started before the server, since nothing proves it never held a lock. Explicit resume requests (`--resume`, `--fork`, headless `--session-id`, and dsh-tui's `DSH_TUI_RESUME_SESSION` handoff) and processes previously observed holding a lock do not use this empty-chat state: after `/new`, a TUI drops its lock until the next message and the pane uses the terminal fallback meanwhile. Missing or ambiguous bindings use the terminal fallback.

The store boundary follows the foreground process’s `DSH_HOME`, or its `HOME` plus `.dsh` when `DSH_HOME` is unset or blank. The session log’s real path must remain inside the real `sessions/` directory. Symlinked store roots are supported; links from a session to an outside log are rejected. The reader pins the file identity and checks it again for conversation and tool-output reads.

The published `@deepseek-ai/dsh-home-paths` package (0.1.7-rc.1 and 0.2.1-rc.2) defines the home override. The `@deepseek-ai/dsh-base` 0.1.7-rc.1 profile configures `session-persistence-jsonl` with `root: !!js dshHomePath('sessions')`. That persistence plugin also accepts a custom `root` through Cordis configuration. Ovis does not evaluate Cordis patches. A custom root outside the standard sessions directory, a relative `DSH_HOME`, or an unreadable process environment uses the terminal fallback. Absolute and home-relative (`~/…`) `DSH_HOME` values are supported.

The reader shows human messages, assistant text and recorded reasoning, tool calls, tool results, and turn completion. System instructions and runtime user-message injections stay hidden. Compaction checkpoints appear as compaction markers; earlier chat remains available. Attachments appear as notices and can be viewed in the terminal.

The newest page contains up to 50 turns. Cursors bind to the session, file identity, and preceding conversation content. Tool output is shortened in the page and can be expanded. Reads limit both compressed input and decompressed output to 16 MiB. Larger logs, unsupported versions, damaged complete frames, and unsupported surface events use the terminal fallback. An unfinished final frame is ignored until its append completes.

This adapter requires Bun with Zstandard decompression support. Session binding currently requires Linux procfs and the same OS user as dsh. It does not add macOS or Windows binding. It reads committed native messages; it does not reconstruct unfinished model streams.

Chat sends use the existing composer. If herdr returns `agent_not_ready` or `agent_not_found`, the composer sends text and Enter through its guarded terminal path. Authorization checks remain active. It does not retry a prompt after an uncertain delivery error.
